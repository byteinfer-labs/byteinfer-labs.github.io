Rune

Faster models with transparent rewrites

Rune is a graph surgery DSL that works on ONNX, TFLite and torch.export graphs and safely rewrites them with easily auditable rules. It refuses rules that produce incorrect graphs. Every time.

Why rewrite a model at all?

  • To run faster. Runtimes only fuse the patterns they recognise; exporters spell things differently.
  • To change the model after export: LoRA adapters, quantization, a prefill/decode split.
  • Often the exported file is all you have. The PyTorch source is gone, or belongs to someone else.
  • Today all of that means a hand-written script, and scripts break models silently.

What does a rule do?

Four things, in order, every time.

  1. 1
    Find

    The rule describes a pattern. Rune finds every place it occurs, all at once.

  2. 2
    Check

    Each change is simulated on a shadow copy. The gate refuses anything that would break the graph.

  3. 3
    Apply

    Only admitted changes are applied, as one transaction.

  4. 4
    Verify

    The rewritten model is run and its outputs compared with the original.

the ruleMul#m -> Add#a -> Relu#r
+ FusedMulAddRelu#f
> m.input[0] -> f.input[0]  ...

Let's see these rewrites in action

Real models, real rules, every output checked against the original.

BERT

12 LayerNorm operations become 1, every time in BERT.

  • BERT-SQuAD from TensorFlow wrote each LayerNorm as 12 ops.
  • ONNX Runtime did not recognise them, so each one ran as 12 kernels.
  • One rule matched all 37 sites and replaced each with a LayerNormalization node.

the rule bert_tf_fusion.rune

Outputs identical to the original, and 5.07% more throughput than ONNX Runtime's own fusion.

LLM serving

One LLM export becomes a prefill model and a decode model.

  • A decoder LLM exported as one graph recomputed attention over the full sequence for every token, with no KV cache.
  • Two rules split it into a prefill graph and a decode graph sharing one copy of the weights.

the rules smollm_prefill.rune smollm_decode.rune

All 512 tokens identical. Decode is 2.67x faster.

SmolLM

126 attention operations become 1, across all 30 attention blocks.

  • SmolLM through Optimum spelled each attention block as 126 ops.
  • ONNX Runtime did not recognise the pattern even though it has the fused kernel.
  • One rule fused all 30 blocks into GroupQueryAttention nodes.

the rule smollm_gqa_fusion_fp16.rune

As accurate as the stock fp16 conversion. Each step is 9.8% faster.

LoRA

LoRA adapters go into an exported LLM, get trained, then fold away.

  • SmolLM exported to ONNX, with no PyTorch model left. The adapters had to go into the graph itself, at 60 projection sites.
  • Two rules wrapped every q and v projection with an adapter chain, keeping the original weights in place.
  • After training in ONNX Runtime, a weight fold and a one-line splice rule merged the adapters back out.

the rules smollm_lora_qv.rune smollm_lora_merge.rune

Injected model bit-identical to the base. Merged model matches within 5e-4, same topology as the original.

Let's watch a good rule

This rule fuses the 12 LayerNorm operations TensorFlow exports into one LayerNormalization node, line by line, then removes the old operations once nothing reads them.

ReduceMean#mean -> Identity#sg -> Sub#center -> Mul#sq -> ReduceMean#var -> Add#addeps -> Sqrt#sqrt -> Reciprocal#rstd -> Mul#gmul -> Mul#mul2 -> Sub#bsub -> Add#lnoutmatch the TensorFlow LayerNorm chain
+ LayerNormalization#ln epsilon=1e-12 axis=-1add one native LayerNorm node
> mean.input[0] -> ln.input[X]route the input to the new node
> gmul.input[1] -> ln.input[Scale]connect the scale weight
> bsub.input[0] -> ln.input[B]connect the bias weight
> ln.output[Y] -> lnout.output[0]wire the output to its consumers
ReduceMean#mean -> Identity#sg -> Sub#centermatch only the start of the chain
! meandelete without rewiring

One rule matches every site in the model, and it's checked before anything changes. Reuse it on any model from the same exporter.

Every run leaves a report

  • HTML and Markdown. What changed, where, and whether the outputs still match.
  • Every site drawn before and after.
  • Runs are versioned. reproduce replays one, diff compares two.
  • query and analyze tell you what a rule would match before you run it.
rune-cli optimize model.onnx --rules rules.rune \
    --report reports/run
rune-cli validate reports/run/optimized.onnx \
    --original model.onnx

Let an agent write the rules

Rune ships its operator runbooks as agent skills. Point your agent at them and it can set up, analyse a model, write a gate-clean ruleset and run it.

They live in .claude/skills/ in the repo. Claude Code picks them up in a checkout; any other agent can read the SKILL.md for the step it is on.

rune-setupinstall and verify the environment→rune-stageanalyse a model, find rewrite candidates→rune-authorwrite and validate rulesets until gate-clean→rune-executerun a validated ruleset with provenance and a report + rune-playgroundwork alongside a person in the browser playground

Rune can also find rules

experimental

  • Point it at a model and it proposes rewrites on its own, no templates needed.
  • Every candidate is checked for numerical equivalence; anything unproven is refused.
  • What passes comes out as an ordinary .rune file you can read, edit and reuse.
  • Conv-net patterns today; transformer patterns are next.
rune-cli discover model.onnx --out rules/

What to know before you start

  • The gate checks structure; verify checks the numbers against the original.
  • A rule matches one exporter's spelling, so another exporter needs its own.
  • ONNX and torch.export are stable; TFLite is experimental.
  • The numbers here come from specific models and hardware.

Found a problem? Open a GitHub issue with the model export, the rule, and the gate’s refusal or audit report.
